# 通用架构设定（技术栈无关，所有项目适用）

> 本文件规定代码结构、命名、模块划分与工程规范，**不允许擅自调整架构分层**。
> 适用范围：任意后端服务、网关、中台、桌面端配套后端；语言/框架可替换，但下文"能力与契约"（分层单向依赖、统一返回与错误码、trace 透传、配置 fail-closed、密钥不入库）不得缺失。
> 各技术栈"用哪个库/工具落地"由团队的《栈能力映射表》另行规定；本文件只定规则。新增技术栈时按同一规则补一套等价落地。

## 1. 整体架构分层

从上至下，**分层单向依赖，上层依赖下层，禁止循环依赖**：

1. **Presentation 表现层**：HTTP 路由 / 接口 handler / 控制器 / 桌面端界面入口。
2. **Service 业务服务层**：业务逻辑、编排、规则、事务边界。
3. **Repository 仓储层**：数据读写（数据库 CRUD、外部存储访问），只读写数据，无业务判断。
4. **Core 核心基础层**：公共类型、错误定义、配置加载、工具函数、领域常量。
5. **Infrastructure 基础设施层**：进程管理、客户端（DB/MCP/HTTP）、日志、环境变量、外部系统适配。

铁律：

- **Handler/Controller 只做参数接收与校验、调用 service、组装返回**；禁止在 handler 写业务逻辑。
- **Service 调用 Repository**；禁止 handler/controller 直接操作 DB 或绕过 service。
- Repository 不反向调用 Service；Core 不依赖任何上层；禁止循环依赖（用依赖倒置接口隔离时，接口定义在下层、实现在上层注入）。
- 横切关注点（认证、日志、trace、限流、错误处理）放在中间件/基础设施，不散落到业务代码。

## 2. 模块目录约定

- 后端按第 1 节分层组织目录；前端/桌面端单独成目录，与后端代码分离。
- 通用固定结构（按栈映射到具体目录名）：

```
project-root/
├── src/（或 packages/<service>/src/）
│   ├── api/        # 路由、handler/controller、DTO（表现层）
│   ├── service/    # 业务逻辑（服务层）
│   ├── repo/       # 数据读写（仓储层）
│   ├── core/       # 配置、类型、错误、工具（核心层）
│   └── infra/      # 进程、外部客户端、中间件、日志（基础设施层）
├── tests/          # 集成测试
├── migrations/     # 数据库迁移（多方言分目录）
├── deploy/         # 部署脚本与配置模板
├── web/ 或 frontend/   # 前端（独立）
└── desktop/ 或 tauri-app/  # 桌面端（独立）
```

- 多包/monorepo：每个可独立部署的服务一个包；共享类型与工具放 `shared`/`common` 包，禁止跨服务直接引用内部目录。
- 空目录用占位文件（`.gitkeep`）保留；生成物、依赖目录、密钥文件一律不入库。

## 3. 命名约定

语言无关原则：命名表达意图、避免缩写（通用缩写除外）、同一概念全项目同名、文件名与内容主责一致。

- **Rust**：类型/结构体/trait/枚举 `PascalCase`；变量/函数/模块/文件 `snake_case`；常量/静态 `SCREAMING_SNAKE_CASE`。
- **Node·TS**：类型/接口/类/组件 `PascalCase`；变量/函数 `camelCase`；常量 `SCREAMING_SNAKE_CASE`；文件：模块 `kebab-case` 或 `camelCase`、组件 `PascalCase`，全项目统一一种。
- 其他语言遵循对应社区惯例，但"类型 PascalCase、常量大写、文件名表主责"的原则保持一致。
- 对外接口 DTO 必须**显式声明序列化字段名**并加校验（类型、长度、范围、必填）；禁止直接把内部实体暴露为外部契约。
- 错误统一收敛为全局错误类型/错误码枚举，不在业务代码里散落裸字符串或随意抛出。
- 异步函数统一使用语言的异步范式；**禁止在异步上下文执行阻塞长耗时操作**，阻塞任务交给专门线程/任务池。

## 4. 配置约定

- 分层配置，至少区分：
  - **用户/全局级**：当前用户或主机的全局配置（如 `~/<app>/config.*`、系统配置目录）。
  - **实例/项目本地级**：当前部署实例目录下的配置，**只允许白名单字段**。
- 加载顺序：默认值 → 全局配置 → 实例本地配置 → 环境变量覆盖；后者覆盖前者，启动时打印**脱敏后**的配置摘要与来源。
- **拒绝未知字段**：出现未声明的键直接报错并指出字段名；实例层出现安全字段（认证开关、密钥、隔离开关、访问白名单）一律拒绝启动。
- **密钥只从环境变量或受控凭证存储注入**（数据库连接串、OIDC 密钥、内部令牌、敏感业务凭证）；禁止写入配置文件、前端静态产物或日志。
- 提供**无任何密钥、含全部合法键与注释**的配置模板。

## 5. 测试约定

- 单元测试随模块（与被测代码同包/同目录），只测一个单元；Service/Repository 必须有单测。
- 集成测试放 `tests/`（或独立测试包），覆盖真实接口与装配。
- 必覆盖四类基础场景：**正常流程、参数非法、权限拒绝、依赖/插件启动失败**；安全相关还要有越权、过期/伪造凭证、隔离缺失等用例。
- 测试不得依赖外部网络或不稳定环境；外部依赖用替身/夹具；副作用测试必须可重复、可清理。
- 重大模块变更遵循 TDD：先写失败测试，再实现。

## 6. 日志约定

- 使用结构化日志，级别至少 `debug/info/warn/error`（可含 trace）；生产用机器可解析格式（如 JSON），开发用易读格式。
- **所有接口入口与外部调用必须打结构化日志，带 trace_id/request_id**；入口日志含方法、路径、状态码、耗时。
- 错误日志必须记录**完整错误来源链（error source/cause）**，禁止吞掉底层错误。
- 敏感信息（密码、token、密钥、Cookie、Authorization、敏感参数）默认脱敏，禁止明文入日志。
- 日志本身的查询受权限控制；日志截断、丢弃、落盘失败必须产生可查询告警。

## 7. Git 与提交约定

- 提交信息遵循 Conventional Commits：`feat:` / `fix:` / `refactor:` / `test:` / `docs:` / `chore:` / `perf:`。
- 禁止提交密钥、`.env`、数据库/状态文件、制品卷、依赖目录、构建产物。
- 锁文件（`Cargo.lock` / `pnpm-lock.yaml` 等）提交入库以保证可复现。
- 一个提交聚焦一件事；重大变更拆小步、先测试。

## 8. 依赖约束

- 优先稳定版依赖，避免直接引用未发布的 git 依赖；新增依赖须说明用途，定期升级与安全扫描。
- 不引入功能重复的库；同一能力全项目只用一个选型。
- 启用依赖治理：**安全公告、许可证、来源/仓库、重复版本**四类检查纳入 CI；许可证采用白名单（未列入即拒绝），传染性/受限许可证需逐项评审并记录例外理由。
- 构建、格式化、静态检查、测试在 CI 中以"警告即失败"方式守门；CI 配置随代码一起评审。

## 9. 接口规范

- RESTful 风格，资源命名一致、用标准 HTTP 方法与状态码；版本化对外契约。
- 统一返回体（全项目固定一种）。推荐：
  - 成功：`{"code": 0, "msg": "ok", "data": <数据>}`；
  - 失败：`{"error_code": "<大写下划线码>", "message": "<对外安全消息>", "trace_id": "<链路号>"}`。
- 统一错误码体系，区分参数错误、认证、权限、未找到、冲突、限流、上游不可用、内部错误；错误码只增不改不重排。
- 状态码语义正确：400/401/403/404/409/429（带 `Retry-After`）/503/500；**5xx 不向客户端泄漏内部细节**，仅给 trace_id 供排查。
- 健康检查端点固定：`/healthz`（存活，恒 200）、`/readyz`（就绪，依赖未就绪如实 503 并给明细）；这两个端点与公开文档是仅有的免鉴权路径。
- trace 透传：入站读 `x-trace-id`（校验格式，非法/缺失即生成），出站写回响应头，并贯穿日志、下游调用与审计。
